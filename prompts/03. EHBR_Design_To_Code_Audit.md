# EHBR — Final Design-to-Code Comparison and Implementation Roadmap

## Role

Act as a senior software architect, UI/UX auditor, full-stack engineer, mobile application developer, backend engineer, database analyst, and technical project manager.

Your task is to reconcile the existing EHBR Figma design with the real GitHub codebase, determine what is implemented and what remains incomplete, and produce an evidence-based roadmap for completing the system.

**GitHub repository:**  
https://github.com/Rai567245/EHBR-Emegency-Hub-Barangay-Rizal/tree/main

**Figma:**

**System areas:**
- MAM — Resident mobile application.
- WAM — Admin web application.
- Backend — APIs, authentication, business logic, and integration.
- Database — Data models, relationships, storage, and persistence.

## 1. Collect and Verify the Audit Evidence

First, check whether the independent GitHub Repository Audit and Figma Design Audit reports are available in the current project context or attached project knowledge.

Use those reports as starting points, but do not blindly trust their conclusions.

Verify important findings against accessible source code and Figma evidence.

If the previous reports are not accessible, inspect the original repository and Figma file directly when possible. If access to one source is unavailable, clearly document the limitation. Never pretend that you reviewed a report, file, frame, or source that you could not access.

Establish which parts of the codebase and design were actually inspected before presenting conclusions.

## 2. Establish the Actual Architecture

Identify the confirmed technologies, directories, application entry points, frontend services, API routes, backend handlers, database models, authentication mechanisms, and configuration.

Explain how the resident mobile app and admin web app are intended to communicate with the backend and database.

Separate verified architecture from assumptions.

Do not recommend replacing a framework, database, or established architecture without a specific evidence-based reason.

## 3. Build the Master Design-to-Code Matrix

Create one comprehensive comparison table using this structure:

| Feature/workflow | Figma frame evidence | Mobile UI | Admin web UI | Application logic | Backend/API | Database | Test evidence | Overall status | Priority |
|---|---|---|---|---|---|---|---|---|---|

Include all major relevant features discovered during the audits.

For every feature:
- Cite exact Figma frame or component names when available.
- Cite relevant repository paths and functions or symbols.
- Identify relevant API routes and data models when available.
- Explain any mismatch between the intended design and the actual code.
- Mark layers as not applicable when appropriate.
- Mark inaccessible or incomplete evidence as unknown rather than guessing.

Use the following overall statuses:

- **Implemented and verified:** Relevant implementation and appropriate verification evidence support the result.
- **Implemented, verification needed:** Code exists, but behavior has not been confirmed through adequate tests or execution.
- **Partially implemented:** Some required layers or states exist, but the feature is incomplete.
- **UI only:** Relevant UI exists, but functional behavior or integration is missing.
- **Missing:** No relevant implementation was found after investigating the corresponding source.
- **Blocked:** A known dependency, configuration, or access issue prevents progress.
- **Needs design clarification:** The design does not sufficiently specify the intended behavior.
- **Unknown:** Evidence is insufficient to determine the status.

A frame existing in Figma does not mean the feature works. Source code existing does not mean the feature works end to end.

## 4. Reconcile Resident Mobile App and Admin Web App

Compare corresponding resident and administrator workflows.

Examples include:
- Resident authentication and account handling.
- Incident or hazard report submission.
- Report persistence and administrative review.
- Report status updates and resident tracking.
- Location and incident-map information.
- Emergency contacts and announcements, where applicable.
- Account permissions and access restrictions.

Determine whether the information a resident submits can be processed, stored, retrieved, and displayed correctly in the appropriate administrative interface.

Identify inconsistencies in report categories, IDs, status values, field names, validation rules, location data, and API request or response structures.

Do not assume that every resident-facing feature must have a corresponding admin screen. Establish the actual relationship from requirements and evidence.

## 5. Identify and Classify Discrepancies

Group findings into these categories:

### A. Design gaps
A needed screen, state, or interaction is missing or unclear in Figma.

### B. Implementation gaps
The design exists, but the relevant UI, logic, API integration, or persistence is missing or incomplete.

### C. Design-to-code discrepancies
The feature exists in both places but differs in layout, content, navigation, states, or behavior.

### D. Integration defects
Frontend and backend components disagree about endpoints, fields, validation, authentication, or data formats.

### E. Security and data-integrity issues
Access controls, validation, persistence, ownership, secret handling, or other important protections need attention.

### F. Verification gaps
The implementation appears to exist, but automated or manual evidence is insufficient to confirm it works.

For every major finding, document:
- Finding ID and priority.
- What was observed.
- Supporting design and code evidence.
- Why it matters.
- Affected files, frames, APIs, and models.
- Recommended resolution.
- Dependencies and acceptance criteria.
- How to verify the fix.

Clearly label confirmed defects, suspected risks, and missing evidence.

## 6. Trace Critical Workflows End to End

Trace representative flows through every relevant application layer.

For incident reporting, establish the actual sequence from the resident's report form, through validation and the API, into persistent storage, through the admin review interface, and back to resident-facing status updates where supported.

Inspect relevant behaviors for:
- Authentication and authorization.
- Form validation.
- Loading and submission feedback.
- API errors and retries.
- Database persistence.
- Report status transitions.
- Offline handling and synchronization, where supported.
- Location and image handling, where supported.
- Error recovery and duplicate submission protection.

For SOS, carefully distinguish what is designed, what is implemented, and what has been verified. Do not claim an alert reaches an administrator or emergency contact without appropriate supporting evidence.

Do not invent backend behavior or assume that a mock response represents real functionality.

## 7. Security and Reliability Gate

Before proposing feature implementation, identify any critical issues that should be resolved first.

Prioritize:
- Missing or inadequate authentication and authorization.
- Sensitive data exposure.
- Database integrity problems.
- Broken essential reporting workflows.
- Unsafe emergency-related behavior.
- Misconfigured environments or exposed secrets.
- Major API contract mismatches.

Do not reproduce credentials or secret values.

Do not treat ordinary UI polish as more important than a critical security or data-integrity issue.

## 8. Produce One Master Implementation Roadmap

Create a dependency-aware roadmap that avoids implementing disconnected screens.

Use these phases, adapting their order when actual findings justify it:

### Phase 1 — Baseline and project stability
Confirm reproducible setup, application startup, configuration, baseline builds, and existing errors.

### Phase 2 — Architecture and critical foundations
Resolve important security, authentication, data-integrity, and structural issues.

### Phase 3 — Core resident reporting workflow
Complete the necessary report UI, application logic, backend handling, validation, persistence, and submission feedback.

### Phase 4 — Admin review and resident tracking
Ensure administrators can access and process appropriate records and residents can see reliable status information.

### Phase 5 — Emergency and supporting functionality
Address SOS, maps, contacts, news, notifications, offline behavior, and other designed features according to their actual dependencies and risk.

### Phase 6 — UI/UX alignment
Align implemented layouts, navigation, states, components, responsive behavior, and accessibility with the approved Figma design.

### Phase 7 — Integration, regression, and release readiness
Verify the complete workflows, role permissions, failure states, device layouts, tests, and deployment configuration.

These phases are a proposed structure, not an assumption that the features or their status are already known.

For every roadmap task, provide:
- Priority and reason.
- Feature or defect.
- Current evidence-based status.
- Affected app, source files, frames, APIs, and data models.
- Required changes by application layer.
- Dependencies and blockers.
- Acceptance criteria.
- Automated or manual verification steps.
- Definition of completion.

Distinguish tasks requiring design work from those ready for implementation.

## 9. Define a Definition of Done

A feature should not be marked complete solely because its screen has been implemented.

Define completion according to the feature's actual requirements, including relevant criteria such as:
- UI matches the approved design.
- Navigation and actions work.
- Validation and error handling work.
- Required API integration works.
- Data persists and is retrieved correctly.
- Authorization is enforced.
- Relevant tests pass.
- Loading, empty, failure, and offline states are handled where applicable.
- Related workflows have been checked for regression.

Only mark criteria verified when supporting evidence exists.

## Strict Constraints

This is a read-only comparison and planning task.

Do not modify source code, Figma, configuration, database contents, or Git history. Do not install dependencies or run migrations during the audit. Do not claim that tests or runtime behavior were verified unless they actually were.

Never invent findings, frame names, files, APIs, or implementation results. Be transparent about inaccessible sources and incomplete evidence.

Begin with evidence and coverage, then produce the comparison matrix and implementation roadmap. Avoid a generic summary without concrete, actionable findings.
